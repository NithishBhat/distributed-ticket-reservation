Distributed Sport Ticket Reservation Platform
System Description
We are building a distributed sport ticket reservation platform that simulates flash-sale traffic where thousands of concurrent users compete for limited event capacity. The system focuses on scalability, concurrency control, and consistency under high contention.
The platform is implemented using Go-based microservices, deployed on AWS ECS. Infrastructure is provisioned and managed using Terraform, and system behavior under load is evaluated using Locust to simulate realistic flash-sale traffic patterns.
Codebase Architecture
Our system is structured as lightweight, containerized Go microservices that communicate over HTTP/JSON APIs. Each service is stateless and independently scalable.
1. Event Service
The Event Service manages event metadata and ticket capacity. It stores event details, including total ticket capacity and the current number of reserved tickets, and exposes read-only endpoints for client access.
APIs:
GET /events
GET /events/{id}
This service is read-heavy and scales horizontally behind a load balancer to support large volumes of concurrent browsing and availability checks during traffic spikes.
2. Reservation Service
The Reservation Service handles ticket reservation requests and enforces the core invariant:tickets_reserved ≤ total_capacity.It validates the requested ticket quantity for a given event and atomically updates the tickets_reserved count using either:
A database transaction with row-level locking, or
A conditional update that ensures capacity is not exceeded.
If remaining capacity is insufficient, the request is rejected.
API:
POST /reserve
This service is write-heavy during flash-sale events and operates under a CP model, prioritizing consistency over availability to prevent overselling.
3. API Gateway
The API Gateway acts as the system entry point. It routes incoming traffic to the appropriate backend services and applies simple rate limiting to protect the system during flash-sale spikes.
Deployment Model
Each service runs as:
A separate Docker container
Deployed on AWS ECS (or Kubernetes-compatible infrastructure)
Scaled independently based on load metrics such as CPU utilization or request rate
All services are stateless and do not store local state, enabling safe horizontal scaling without data loss.
Infrastructure is fully managed using Terraform to ensure reproducible deployments and consistent experimental environments.
Experiments
Experiment 1: Horizontal Auto-Scaling
We use Locust to simulate flash-sale bursts across varying ECS instance counts provisioned by Terraform.
Metrics collected:
Throughput (requests per second)
Latency percentiles (p50, p95, p99)
Error rate
Auto-scaling reaction time
Experiment 2: Distributed Locking Strategies
We compare multiple concurrency control mechanisms under high contention using Locust.
Goals:
Validate correctness (no overselling)
Measure throughput under contention
Evaluate retry rates and latency tradeoffs across locking strategies
Experiment 3: Caching Layer Impact
We generate read-heavy mixed workloads with and without a caching layer. Terraform toggles the cache infrastructure between experimental runs.
Metrics collected:
Database load reduction
Read latency improvements
Cache hit rate
Overall system throughput
Experiment 4: Data Consistency Under Failure
We simulate node failures and network partitions mid-transaction by killing and restarting ECS tasks during peak Locust load.
Validation criteria:
No data corruption
No overselling
Recovery time
Transaction loss rate
